# JobPilot 架构说明

## 当前工作流

```mermaid
flowchart TD
    R[简历正文与一次岗位意向] --> X[AI 提炼并验证原文]
    X --> A[CandidateProfile 真实材料]
    A --> D[统一岗位与规则过滤]
    B[实习僧 HTTP / 牛客浏览器 / BOSS 扩展 / Mock] --> C[普通工具分派或 MCP Client + Server]
    C --> D
    D --> E[去重与 Tracker]
    E --> F[JobAnalyzer 结构化 JD 与原文引用]
    F --> G[CandidateMatcher 真实候选人证据]
    G -->|只搜索匹配| L[记录结果并处理下一岗位]
    G -->|包含沟通草稿| H[GreetingGenerator 草稿]
    H --> I[PendingAction 完整快照和摘要]
    I --> J[LangGraph Interrupt 等待人工审批]
    J -->|拒绝| L[记录结果并处理下一岗位]
    J -->|批准| K[原子领取批准并执行]
    K -->|结果明确| L
    K -->|结果未知| M[暂停并人工核查]
    M -->|记录核查结果后恢复| L
    L -->|还有岗位| F
    L -->|新搜索全部比较完成| N[评分排序并复核前五名]
```

图遍历结束后进入 COMPLETED。图内的旧发送执行边已用模拟动作测试；新版 BOSS 批量联系在搜索完成后单独审批和执行，见下文。首次真实联系仍待本人批准后验收。

实习僧和牛客已通过有限真实数据验收。实习僧使用公开 HTTP；牛客复用已登录的专用 Edge 持久资料，通过 Playwright 只读搜索和详情。两个平台沿用公开分页，每个关键词最多 20 页，并记录是否读到末页；BOSS 新页面改为普通浏览器扩展桥接，已通过当前账号的有限真实读取与匹配验收。`PublicPageReader` 只发送公开 GET，校验平台主机和路径、限制跳转与正文大小、请求至少间隔一秒。401/403/429 或登录验证会暂停，不切换指纹、不解验证码，也不读取浏览器 Cookie。`ShixisengAdapter` 从列表取编号，再解析详情；必要字段含特殊字体时，搜索跳过该条并记录 read_warnings，可选字段保留未知；全部详情不可读则失败。验证码、403、限流不属于可跳过的错误。两种读取器共享 `PageReader` 契约，后面的服务不依赖传输方式。

Dashboard 默认 `analysis_only=true`；CLI 使用 `--analysis-only`。该模式在分析后进入下一岗位，不创建草稿或 PendingAction；新页面额外在全部比较后排序、复核前五名。原有任务和未指定该字段的 API 请求保持旧流程。`discovery` 与 `rejected_jobs` 保存读取数、排除原因和去重数，避免把零匹配误判成零数据。这里只验证技能证据，不能据此认定学历、毕业年份、语言或招聘有效期均符合。

| 层 | 职责与边界 |
| --- | --- |
| models | Pydantic 领域数据，不携带连接、浏览器或密钥 |
| adapters + browser | 读取各平台页面并标准化；选择器集中在 selectors.py |
| llm | Chat Completions / Responses 两种严格 JSON Schema 接口；DeepSeek 使用后者；offline 只是有限词表替身 |
| services | 确定性规则、引用校验、技能匹配、草稿与审批，不依赖招聘网站 |
| tools | 普通 Tool Calling 的本进程参数校验和方法分派 |
| mcp_client / mcp_server | 同一组只读工具的真实 MCP 握手、stdio 和子进程传输 |
| workflow | LangGraph 的 State、Node、Edge、Loop、Interrupt 与恢复 |
| storage + migrations | 业务关系表、审批事务和版本化迁移；检查点交给 LangGraph Saver |
| api + web | 单机令牌鉴权、有限工作线程、状态查询、SSE 与中文界面 |
| evaluation | 人工标注合成样本、独立指标、恢复注入与浏览器验证 |

搜索数量通过 search_limit 从 API/CLI 保存进任务，恢复时仍用原值。普通工具与 MCP 都在打开 Adapter 时设置读取上限；source_warnings 经工具、协议和检查点传到界面。两个平台每个关键词最多 20 页，重复页、禁用的下一页按钮和可见空结果都会停止翻页；HTML 的隐藏模板不能作为零结果证据。

## BOSS 只读桥接

`BossExtensionAdapter` 把查询词和数量上限交给本机 `BossBridge`，没有结果时抛出原有 BrowserPausedError，LangGraph 在读取节点保存检查点。扩展面板通过普通 tabs/scripting API 读取可见 DOM，逐条向独立桥接接口回传；后端重建 BOSS 岗位身份、限定详情域名和路径，再交回原图。Filter、Matcher、Ranking 不依赖扩展。

桥接进度单独保存在本机 SQLite，包含已读岗位、尝试编号、覆盖警告和 60 秒读取租约。验证需要人工继续；助手关闭后可恢复已授权的只读搜索。结果齐备只自动恢复等待浏览器的 analysis_only 任务，不恢复模型失败、不批准动作。配对凭据一天过期，可领取读取任务及已批准的联系目标、提交对应结果，不能访问候选人、密钥、审批或任意命令。连接通过本机首页转交，凭据不进入网站查询参数。

新桥接仅用于 API direct 路径；原 CLI/MCP BOSS Playwright 入口保留诊断用途。普通 Tool Calling 与 MCP 的调用边界没有合并。BOSS 城市目前在后端强制筛选，不改网站保存的城市选择；先通过公开下一页按钮或岗位列表滚动收集链接，再读取详情，不调用隐藏 API。保存每次列表的公开岗位编号，用于验证续页确实带来了新岗位。浏览器资源一直加载时，可用已就绪的 DOM 读取正文，但等待导航提交期间不能使用旧页面。

## BOSS 批量联系与批准

搜索结果不自动变成申请。`batch.js` 让用户从已完成结果中选最多 20 个岗位；`boss_contact.py` 复用 PendingAction 保存目标快照和明确的操作说明。默认全部未勾选，用户核对 BOSS 账号、默认招呼、在线简历并主动批准后，后端才将这一批动作在同一数据库事务中改为 APPROVED。列表变化会撤销页面上的旧确认。

扩展不能批准。`contact.mjs` 先检查当前详情的岗位编号、名称、公司和唯一的“立即沟通”按钮，再向后端申请 15 秒单次许可。后端在文件锁和条件更新下将 APPROVED 改为 EXECUTING；重复领取失败。扩展在隔离环境内再次核对目标及许可期限，只点击一次。选择器集中在 selectors.py。这里不上传附件、不发送 AI 草稿、不读取聊天；实际可能发送网站默认招呼并展示在线简历，审批前明确告知。

原岗位显示“继续沟通/已沟通”才记为 SUCCEEDED 并推进 Tracker 至 CONTACTED。回执不明或发出许可后 90 秒无回执进入 UNCERTAIN，阻止后续批次和自动重试；用户在网站核查后才可记录结果。网页需要人工处理但尚未发放许可时保持 APPROVED 并暂停，可继续或取消。进程重启保留全部状态；若动作成功已保存而 Tracker 尚未更新，重复回执或后续查询会补齐跟踪记录。旧 send_message 草稿沿用原摘要算法。

搜索图的 Checkpoint 继续负责提炼、读取和匹配恢复；每个批量动作通过 `contact_graph.py` 进入独立的 LangGraph 联系图，并以原搜索 run_id 关联。图只理解 PendingAction 状态，不依赖网站、选择器或浏览器。`observe → wait_for_event → observe` 循环使用 Conditional Edge 和 Interrupt，覆盖待批准、待浏览器、待执行、待回执、待核查；拒绝或成功后进入 END。直接 Resume 不会改写批准状态。

联系图以 `action:<动作编号>` 区分线程，与搜索图共用 `checkpoints.py` 选择的 SQLite/PostgreSQL 后端。动作表仍是批准与单次领取的权威记录，图保存可恢复位置；只有图到达 READY 才开放领取，先保存 EXECUTING 检查点再把许可交给扩展。两次数据库提交之间进程中断时，以动作表补齐图，不能为已领取动作再次发许可。状态不变的轮询不新增检查点。主 API 提供 `/api/boss-actions/{id}/workflow` 查看恢复位置，扩展凭据不能访问；页面继续只显示普通中文状态。

```mermaid
flowchart LR
    A[observe 读取持久动作] --> B{当前状态}
    B -->|等待批准、浏览器或人工核查| C[wait_for_event 保存位置并暂停]
    C -->|用户决策或浏览器回执| A
    B -->|已成功或已拒绝| D[END]
```

当前按本机单个 BOSS 账号跨任务防重复联系；账号身份自动核验、多账号调度、附件投递、自定义消息和真实端到端联系验收仍未完成。

## 证据和副作用约束

新页面通过 `/api/search` 提交正文与一次岗位意向，固定只读。`extract_profile` 节点调用 AI 生成 ResumeExtraction，再检查姓名、经历和引用确实位于原文、技能完整名称匹配、可用时间有数值引用；否定或计划语句不升级为已有技能。提炼后保存 CandidateProfile 和搜索词到检查点，不需要另点确认。原 `/api/resume/profile` 人工整理接口保留兼容测试及开发调用。原始文件不保存，正文会作为任务输入持久化，真实模式会发给模型。

新搜索的 `search_filter` 只强制城市、明确工作类型、下线和截止日期；目标标题和实习时间从旧 RuleFilter 中暂时解除。旧 CLI 和非排名任务仍使用原严格 RuleFilter。JobAnalyzer 根据原文提取要求并判断意向 related/adjacent/unrelated/unclear，引用也必须来自 JD；明显无关的职业保留排除原因。

CandidateMatcher 仍逐项核对证据，只增加明确的名称缩写等价（例如 JS/JavaScript），不把相关技术当成已掌握。ranking_service 用技能 70、意向 20、时间 10 的分项公式排序；必需技能权重 3，加分项权重 1，学习中计半分。天数和月数各最多扣 5 分，没有填写的信息留待确认。评分是可解释的启发式，不是经标定的录用概率。

每条分析结果落盘后才进入下一条；`rank` 节点排序，`refine` 每次调用一次 AI 复核前五名中的一条。AI 选择已核验证据序号和顾虑原句；程序校验序号、状态和引用再组织理由，拒绝把缺失技能变成已有经历。refine 中断后从未完成的条目继续，不重新提炼简历或重跑已经完成的岗位。

JD 结构化输出仍要逐项核对原文引用。CandidateMatcher 只匹配 CandidateProfile 中明确出现的技能与证据；学习中的技能不能升级成已熟练。模型只选择草稿证据编号，程序引用用户原文组织文本，不自由补写项目经历。Pydantic 保证结构，不保证经历真实，输入材料的事实仍需用户确认。

PendingAction 保存候选人、岗位、正文和证据的完整快照，SHA-256 摘要绑定审批内容。批准不等于立即可靠送达。执行器先原子地将 APPROVED 改为 EXECUTING，只读预检查失败可以恢复批准；进入发送后任何未知结果都成为 UNCERTAIN，禁止自动重试。

EXECUTING/UNCERTAIN 会中断图。人工核查接口取得同一工作流锁，再核对摘要、保存核查人和依据。确认未发送会终结该动作，后续重新发送需要新任务与新批准。Tracker 随分析和草稿推进；只有非模拟动作的成功回执或人工送达确认才记录 CONTACTED，不覆盖已经记录的面试、归档等进展。

## 状态、恢复和数据库

AgentState 只保存 JSON 数据，完整图状态由 thread_id 对应检查点持久化。恢复时使用原来的 run_id、source、mode、transport 和数据目录。Resume 不能批准动作，也不会重发未知结果。读取节点遇到登录或验证码时中断；模型暂时失败保留失败节点，按恢复位置继续。

原 Phase 1 SQLite 文件保持兼容。后续支持关系后端 pending_actions、agent_candidates、agent_jobs、agent_applications、agent_runs；SQLAlchemy 负责方言差异，Alembic 负责业务表升级。SQLite 初始化也通过迁移，旧的无版本库只有结构完全吻合已知版本才补记版本，否则保留数据并停止。PostgreSQL Saver 单独维护检查点结构。

CLI 的历史默认库和 API 的默认库不同，详见 demo.md，不能只拿相同 run_id 就假定共享同一任务。Checkpoint 不是数据库备份；迁移不自动搬迁历史库。

## 浏览器和运行边界

浏览器资料按平台独立保存，文件锁阻止同一资料并发打开，Chromium 沙箱显式启用。普通 Edge 人工登录只启动可见窗口，不自动填写认证表单。后续读取仍受可信 HTTPS 主机校验、请求数量上限和导航间隔约束。空白页、登录验证、拒绝访问或选择器缺失都明确暂停或报错，不伪装成空岗位列表。

页面就绪要求结果元素可见，BOSS 导航栏中的 `/job_detail/` 入口和隐藏空结果模板不算岗位结果；检查验证弹窗时考虑所有匹配元素，避免漏掉隐藏模板之后的可见弹窗。`browser_cli diagnose` 只访问一次主页并观察主框架导航，遇到异常即停；本机报告仅含类别和有限状态，不保存原始 URL 或认证资料，也不把打开页面当成登录验收。

API 默认只监听本机，校验令牌、Host、Origin 和请求频率；界面用 textContent 展示外部内容。同步图放入单个受限工作线程，SSE 异步输出状态快照。日志轮转且只记录白名单字段，密钥和简历正文不进入事件日志。

SSE 连接定期结束后，页面先读取最新快照，任务仍执行时续接状态流；失败和完成时停止；BOSS 等待助手的只读暂停仍查询进度，以便自动显示匹配结果。连续三次网络错误会提示用户重新选择任务，切换任务时取消旧连接。续接只使用 GET，不重复执行任务、批准动作或发送消息。

当前没有多主机并发需求，因此使用文件锁和本机队列，没有引入 Redis。MCP 是接口与传输边界，不是权限沙箱；其工具不暴露任意 URL、脚本或外部发送。容器和真实 PostgreSQL 尚未在本机验收。

评估门禁独立于指标计算：`evaluation/gates.py` 读取阈值，检查测量分母、有限数值和上下限。零候选人证据幻觉是不可关闭的约束。离线基线只用于发现回归；真实服务未测时不会把未知用量或成本写成成功。CLI 出错也写入失败报告并返回非零，CI 可以据此阻止发布。

恢复请求先持久化 QUEUED，再提交后台线程，因此返回 202 后不会仍显示上一轮的 PAUSED。若线程池已关闭，恢复原状态并明确报错。部署验收使用独立 Compose 项目和随机测试凭据，不读取个人 .env 或复用数据卷；HTTP 恢复客户端仅允许本机回环地址和 Mock 操作。

## Phase 0、1 原始 CLI 设计记录

下文保留最初阶段的设计说明，仅描述原 `app.main`。其中“后续阶段”是当时的规划；当前实现和限制以上文及 phases.md 为准。

当前数据流是同步的普通 Python 调用。没有后台 Agent、浏览器或 API 服务。候选人配置和 Mock 岗位均从本地 UTF-8 JSON 读取，输出是 CLI 展示与 SQLite 记录。

## 模型为什么用 Pydantic

`DomainModel` 统一禁止未知字段并开启赋值校验，尽早发现配置拼写错误。核心字符串不允许空值，天数限于 1–7，月份必须为正整数，时间必须携带时区。`CandidateSkill` 将技能、用户自述等级和证据放在一起，避免只有标签、没有依据。

`JobPosting` 不含 selector、浏览器对象或候选人数据。空 JD 可以进入模型，随后由 RuleFilter 给出明确的拒绝原因。`Application` 通过 candidate_id 与 job_id 表示某个候选人的状态，而不是让岗位自身携带全局申请状态。

Pydantic 不证明输入经历真实；它只保证结构与字段约束。后续生成模块还必须只引用用户提供的事实。

## Adapter 为什么只负责读取

`JobSourceAdapter` 定义 search_jobs 和 get_job_detail；Mock 实现按文件名稳定排序，整批校验 JSON。如果一个文件损坏，报告文件名并停止，避免误把部分数据当成完整结果。

本轮不创建 BOSS 空壳或 prepare/send 方法，因为这些属于后续 Phase。未来平台 Adapter 只需输出相同 JobPosting，过滤、去重、存储无需知道平台页面结构。

## 规则为什么独立于 Adapter

`normalize_job` 清理格式与 URL；`RuleFilter` 接收候选人和岗位，返回 passed 与全部 reasons。排除岗位检查标题，排除关键词检查标题和 JD；标题须包含目标岗位或显式配置的偏好词之一。英文匹配有词边界，避免 AI 意外命中 retail。

城市支持杭州、上海、深圳的英文别名以及 Remote/远程等显式别名，不猜测任意位置。明确的实习岗位会检查候选人的时长与每周到岗约束；缺失元数据按未知保留。示例中的 preferred_keywords 参与粗筛，并非技能匹配分数。

标准化、过滤、去重都是纯本地确定性操作，因此不需要 LLM，也不需要为这些步骤引入框架。

## 去重如何识别同一岗位

本批次按 `(source, source_job_id)` 或 canonical URL 判断重复，保留第一次出现的记录。URL 删除 fragment 和已知跟踪参数（utm_*、gclid 等），保留 id/job_id 等身份查询参数；不通过公司、标题和城市猜测两个招聘编号相同。

数据库以 `(source, source_job_id)` 唯一约束保证跨次运行的幂等性，另外在写事务内比较已有岗位的规范 URL。再次导入相同平台岗位或 URL 别名时，保留最初的本地 ID 与平台身份，更新岗位快照，维护既有申请链接。`resolve_job_id` 让 CLI 使用已保存的身份创建或读取申请，不会因编号别名重新生成 NEW 状态。URL 比较采用简单扫描，适合当前 20 个岗位的规模；跨平台 duplicate_group_id 和岗位编号/URL 的完整别名历史尚未实现。

## SQLite 为什么足够

本阶段仅本地同步读写，标准库 sqlite3 即可。候选人与岗位保存为 JSON，业务身份放在关系字段中；申请表保存状态、时间、备注和最后动作。

约束：jobs 的平台身份唯一；applications 的候选人/岗位组合唯一；外键拒绝不存在的候选人或岗位。所有写 SQL 使用参数绑定。每个写方法独立开启事务，save_jobs 中任一冲突会回滚整个岗位批次。上下文管理器负责关闭连接，不表示整个搜索是单个事务。

搜索中断后可以再次运行，唯一约束会阻止重复记录；这还不是 Agent checkpoint 恢复。现阶段没有 AgentRun、状态迁移工具或 PostgreSQL。

## 状态与用户确认

搜索后自动创建 NEW 记录，仅表示“已纳入本地跟踪”。所有手动状态/备注修改都要求 `confirmed=True`；CLI 只有同时给出具体 `--set-status ID STATUS --confirm` 才会传递此值。

这是一款本地 CLI 的交互契约，不是多用户认证机制，也不是外部动作批准令牌。状态允许列表位于 tracker.py，阻止 NEW 直接变成 OFFER 等无效流转。记录 CONTACTED 仅用于用户录入线下进展，不调用任何外部平台。

后续 Phase 4 才会加入 PendingAction 和对具体待发送内容的批准；当前没有发送/投递执行能力。

## 配置、日志与异常

配置按环境变量、项目 .env、默认值依次取值，不修改进程环境。标准库 logging 输出 run_id、节点/工具、计数、耗时和失败原因，DEBUG 额外记录 job_id 及过滤结果。CLI 展示集中在 main.py 使用 print，其他模块不直接展示业务结果。

可预期错误使用 JobPilotError 子类，CLI 返回非零退出码。候选人校验只报告字段位置，不输出完整个人资料。默认测试完全离线；真实浏览器测试在将来的 Phase 3 单独建立。

## 本机模型设置与新手入口

页面左侧只有一个面板：简历正文、一次意向、城市、可选时间和网站。示例填写同一套可编辑输入；删除手填技能卡和重复岗位输入。点击搜索一次性读取当前表单，右侧显示自动提炼的原文、评分和详细复核；没有另一份“已确认资料”。启动器等待服务启动后，用 URL 片段传入本机连接码；重复启动先通过鉴权的 `/api/instance` 核对数据目录，再重新打开原服务。页面立即移除片段；连接码保存在当前页面会话的 sessionStorage，刷新后可继续使用。它不进入 HTTP URL、访问日志或持久的 localStorage。API 继续校验 Host、Origin 和请求凭据，不因简化界面取消鉴权。

`model_settings.py` 只允许页面保存固定的 DeepSeek 服务地址和模型，不接收任意远程地址。先写临时文件，再原子替换 `.env`，保留其他配置；存在更高优先级的进程环境变量时明确拒绝覆盖。所有返回值均不包含服务密钥，校验错误也不回显输入。密钥不保存到浏览器存储。

连接测试是独立、显式的模型请求，只使用固定测试文字并校验结构化结果。保存设置不会触发模型请求或创建求职任务。DeepSeek 使用 Responses 的 `text.format.json_schema`，关闭思考并限制输出长度；本地继续拒绝截断、拒答、工具调用和伪造引用。已有 Chat Completions 协议保留，接口不兼容时明确报错，不自动切换离线结果。
